Project Overview

AMRPredict is a full-stack machine learning system developed as a Final Year Project (FYP) in BioInformatics & Machine Learning. The project addresses the global health crisis of Antimicrobial Resistance (AMR), which the WHO lists as one of the top ten global public health threats facing humanity.

The system predicts whether a bacterial sample is Resistant or Susceptible to a specific antibiotic. It uses two machine learning models trained on real genomic data from the BVBRC/PATRIC database. A third component simulates how resistance can spread through a bacterial population week by week, using a biologically grounded logistic growth model.

The idea behind this project is to show that machine learning applied to genomic data can predict antibiotic resistance faster and more affordably than traditional lab culture tests, giving clinicians useful information within minutes rather than waiting days for results.

Project Objectives
01
Binary Resistance Classification
Train a LightGBM model on 90,826 labeled AMR records to classify antibiotic resistance from genomic metadata with AUC-ROC ≥ 0.90.
02
Alignment-Free Genomic Prediction
Build a k-mer frequency RandomForest model that predicts resistance directly from raw FASTA sequences without needing any reference genome alignment.
03
Temporal Resistance Forecasting
Simulate week-by-week resistance evolution using a biologically-calibrated logistic growth model parameterised per antibiotic class.
04
Production-Ready Web System
Deploy all models as a full-stack REST API system (Django + Flask) with an interactive web interface for clinical and research use.
Methodology
Phase 1: Data Collection and Preprocessing

AMR phenotype data including Resistant, Susceptible, and Intermediate labels, MIC values, and organism metadata was downloaded from the BVBRC database across more than 15 bacterial species. FASTA genome sequences were collected for 1,685 isolates. The data was then cleaned to remove duplicates, parse MIC strings, extract genus and species from genome names, and merge Intermediate labels into Resistant for binary classification.

Phase 2: Feature Engineering

Two separate feature sets were built: (1) 14 tabular features for LightGBM, including MIC value, log, and sign, drug class, genus and species, as well as target-encoded resistance rates per antibiotic, taxon-antibiotic pair, and genus-antibiotic pair; and (2) 256+ k-mer features for RandomForest, extracted from the 4-mer frequency spectrum of raw FASTA sequences along with GC content and antibiotic one-hot encoding.

Phase 3: Model Training and Evaluation

LightGBM was trained with is_unbalance=True and early stopping (30 rounds) on an 80/20 stratified train-test split. The K-mer RandomForest used class_weight='balanced' to handle class imbalance (no SMOTE required for RF). Both models were evaluated on held-out test sets using AUC-ROC as the primary metric.

Phase 4: Deployment

The trained models are saved to disk as LightGBM .txt and RandomForest .pkl files and loaded when the Django backend starts up through a model registry. The Flask frontend forwards all prediction requests to the Django REST API. All three models include fallback logic so the system keeps working even if a model file is missing.

Known Limitations
Formulation Model Missing
A fourth model (Formulation Forecasting) was planned to recommend optimal dosing strategies but was left out of scope. No publicly available pharmaceutical formulation dataset was found that matched the project's genomic data.
No Real-Time Training Progress
Model training runs in a background thread. There is no WebSocket-based live progress indicator. The interface shows a "Training started" message but does not stream training logs in real time. A production system would use Celery and Redis for async task queuing.
Timeline is Simulation, Not Trained
The Mutation Timeline uses a biologically-informed logistic growth model, not a trained CNN-LSTM. While results are scientifically plausible, they are simulated rather than learned from empirical time-series data.
No User Authentication
The system has no login/authentication layer. In a clinical deployment, HIPAA/GDPR compliance would require user accounts, audit logging, and encrypted data at rest. This is a research prototype.
